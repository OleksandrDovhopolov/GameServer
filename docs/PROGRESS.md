## 3 ноября 2026 — повтор Terraform apply/destroy

- Повторно выполнен полный цикл Terraform: `init` → `plan` → `apply` → проверка ресурсов
  в AWS Console → `plan -destroy` → `apply destroy.tfplan`.
- Через Terraform снова подняты учебные ресурсы в AWS: VPC, subnet, Internet Gateway,
  route table, association subnet с route table, security group и EC2 `t3.micro`.
- Проверено, что после `apply` все ресурсы видны в AWS Console. После `destroy` они удалены,
  а Terraform state снова содержит пустой список `resources`.

### Цепочка AWS-ресурсов

Связь ресурсов проходит сверху вниз:

`VPC` → `subnet` → `route table` → `Internet Gateway` → `security group` → `EC2`.

- **VPC** — изолированная сеть AWS с диапазоном `10.0.0.0/16`.
- **Subnet** — участок адресов внутри VPC, например `10.0.1.0/24`.
- **Route table** — правила, куда отправлять трафик. Маршрут `0.0.0.0/0 -> IGW`
  даёт подсети путь в интернет.
- **Internet Gateway** — шлюз между VPC и интернетом.
- **Route table association** — привязка конкретной subnet к route table; без неё
  subnet использовала бы другую таблицу маршрутов.
- **Security group** — firewall для сетевого интерфейса EC2. В упражнении разрешён SSH
  только с одного IP, исходящий трафик разрешён.
- **EC2** — виртуальный сервер, размещённый в subnet и подключённый к security group.

Terraform создаёт ресурсы через зависимости: сначала сеть и шлюз, затем маршрутизацию,
правила доступа и EC2. При `destroy` удаляет их в обратном порядке, чтобы не оставить
объект, от которого зависят другие ресурсы.

Источники данных `aws_ami` и `aws_availability_zones` ничего не создают: они только находят
подходящий образ Ubuntu и доступную зону. S3 bucket `gameserver-tfstate-bobak` тоже не входит
в этот destroy-цикл: он хранит Terraform state и был создан отдельно до настройки backend.

- `default_tags` на уровне провайдера проставляет `Project`, `Environment` и `ManagedBy`

- Переменная `allowed_ssh_cidr` намеренно без значения по умолчанию, с валидацией, запрещающей

  что у `.env.vps` и `.env.vps.example`.
- Отмечена особенность: AWS разрешает весь исходящий трафик по умолчанию, а Terraform нет.
  Без явного блока `egress` группа безопасности остаётся вообще без исходящих правил.

### Remote state

- Корзина `gameserver-tfstate-bobak` создана через AWS CLI — обход задачи «курица и яйцо»:
  хранилище для состояния должно существовать раньше, чем Terraform сможет им пользоваться.
- Включено версионирование: при повреждении состояния можно откатиться на предыдущую версию.
- Состояние перенесено командой `terraform init -migrate-state`, ключ `learn/terraform.tfstate`.
- Блокировка через `use_lockfile = true`. План предполагал DynamoDB, но начиная с Terraform 1.11
  S3 блокирует состояние сам, а `dynamodb_table` объявлен устаревшим. Знать стоит оба варианта:
  в существующих проектах DynamoDB встречается повсеместно.
- Зафиксировано, что в блоке `backend` нельзя использовать переменные — он обрабатывается
  до вычисления чего бы то ни было. Разные окружения разделяются разными значениями `key`.

### Модули

- Сеть вынесена в [infra/modules/network](../infra/modules/network): пять ресурсов и источник
  данных за интерфейсом из трёх входов и четырёх выходов.
- Провайдер в модуле не объявляется, а наследуется от вызывающего кода — поэтому `default_tags`
  действуют и внутри.
- Перестройка пришлась на пустое состояние, поэтому прошла бесплатно. При живых ресурсах
  смена адресов (`aws_vpc.main` → `module.network.aws_vpc.this`) потребовала бы
  `terraform state mv`, иначе Terraform снёс бы и создал заново.

### Ключевые наблюдения

- `terraform destroy` снёс семь ресурсов одной командой в том же порядке, который 17 октября
  выводился опытным путём по консоли через ошибки «has dependencies». Порядок вычисляется
  из графа зависимостей, построенного по ссылкам вида `aws_vpc.main.id`.
- Источники данных не попадают в счётчик `add / change / destroy`: они читаются, а не создаются.
- `plan` сравнивает три вещи: код (как должно быть), состояние (что Terraform помнит) и ответ
  API AWS (как есть на самом деле). Правка ресурса вручную в консоли будет замечена.
- Terraform не ограничен AWS: провайдеры существуют для Hetzner, Cloudflare, GitHub, Kubernetes,
  Grafana и PostgreSQL. То есть текущий staging-контур тоже можно описать кодом.

## 17–18 октября 2026 — IAM, S3, VPC и сетевые основы AWS

### IAM — права доступа

- Разобраны четыре объекта IAM: пользователь, группа, политика и роль. В политике используются
  `Effect`, `Action`, `Resource` и `Condition`; по умолчанию всё запрещено, явный `Deny` сильнее
  любого `Allow`.
- Созданы IAM-пользователь и группа для работы не под root. На примере
  `AmazonS3ReadOnlyAccess` проверено, что готовые политики удобны, но могут быть слишком широкими
  (`Resource: "*"`).
- Создана роль `ec2-s3-readonly`, S3-бакет и EC2 с прикреплённым instance profile. Команда
  `aws s3 ls` на EC2 сработала без ручного ввода ключей: временные credentials выдаются через
  метаданные и обновляются автоматически. Удаление файла через `aws s3 rm` роль отклонила.
- Практический вывод для OPS-3: Hetzner VPS находится вне AWS, поэтому для отправки backup в S3
  понадобится отдельный пользователь с узкой политикой только на запись в одну корзину.

### S3

- Разобрано назначение S3: бэкапы, дампы, логи, Terraform state, артефакты сборки и крупные
  объекты. Файлы баз данных, требующие быстрых случайных операций, в S3 не помещаются.
- Для будущих backup отмечены versioning и lifecycle rules: защита от случайного удаления,
  перевод объектов в холодное хранилище и удаление по сроку.

### VPC — сеть собрана вручную

- Созданы VPC `learn-vpc` (`10.0.0.0/16`), public subnet `learn-public-a` (`10.0.1.0/24`,
  `eu-north-1a`), Internet Gateway `learn-igw`, route table `learn-public-rt` и EC2 с публичным
  адресом и security group, разрешающей SSH только с одного адреса.
- Проверено восстановление после удаления маршрута `0.0.0.0/0 -> IGW`: SSH пропал, хотя машина,
  security group и публичный адрес оставались. После возврата маршрута доступ восстановился.
- Зафиксировано главное правило: подсеть становится публичной не из-за отдельного флага, а из-за
  маршрута в Internet Gateway. Неудаляемый маршрут `10.0.0.0/16 -> local` сохраняет связность
  внутри VPC.
- Прослежен путь пакета: интернет -> Internet Gateway -> route table -> NACL -> security group
  -> сетевой интерфейс. NAT Gateway для private subnet разобран, но для учёбы не используется
  из-за стоимости около 32 USD в месяц.

### Уборка ресурсов и сетевые основы

- Все учебные ресурсы удалены от листьев к корню: EC2, security group, Internet Gateway, route
  table, subnet, VPC, S3 bucket и IAM role. Дефолтную VPC AWS оставили: она бесплатна и создаётся
  автоматически.
- Замечены оставшиеся security groups `launch-wizard-*` от ручного мастера запуска; это пример
  того, как ручной аккаунт постепенно зарастает ресурсами.
- Повторены сетевые основы: IP, TCP/UDP, TLS и HTTP; CIDR и приватные диапазоны; NAT; DNS и TTL;
  stateful/stateless firewall; `127.0.0.1` против `0.0.0.0`.
- Для диагностики закреплено различие `connection refused` и `timeout`, а также порядок работы
  с `dig`, `ss -tlnp`, `curl -v`, `nc -zv` и `traceroute`.
- Разобраны TLS-сертификаты, reverse proxy и `X-Forwarded-For`. Незакрытая задача SRV-1:
  приложение берёт первый элемент этого заголовка, который клиент может подделать.

### Старт ноябрьского блока: AWS

Остаток октябрьских задач (OPS-2, OPS-3, OPS-4) сознательно перенесён в ноябрь, чтобы не

  разбираться не с чем. Почту закрытого аккаунта AWS повторно использовать не разрешает,
  поэтому новый заведён на алиас того же ящика.
- Создан новый аккаунт, рабочий регион **eu-north-1** (Стокгольм) — один из самых дешёвых
  в Европе. Все ресурсы держим в одном регионе: забытая машина в другом регионе не видна
  в консоли, но тарифицируется.
- Первое упражнение: запущен EC2 t3.micro, подключение по SSH, затем инстанс удалён
  (terminate, а не stop — у остановленной машины продолжает тарифицироваться диск EBS).

Что стало видно на практике:

- У машины на интерфейсе **только приватный адрес** `172.31.x.x`; публичный живёт на шлюзе
  AWS и подменяется при прохождении трафика. На VPS публичный адрес принадлежал самому
  интерфейсу.
- Firewall вынесен наружу: security group — отдельная сущность, машина о ней не знает.
  Поэтому доступ можно вернуть, не заходя на сервер.
- Метаданные инстанса (`169.254.169.254`, IMDSv2) — механизм, через который приложения на EC2
  получают временные ключи от роли IAM. Отсюда правило: в коде на EC2 не должно быть
  захардкоженных ключей доступа.

Решение по архитектуре: **перенос Railway в AWS признан нецелесообразным**. При текущей
нагрузке закрытого тестирования эквивалент в AWS стоил бы примерно в десять раз дороже,
не решая ни одной существующей проблемы. AWS в плане нужен для рынка труда и изучения
Terraform, а не для продукта.

### Исправлен postgres-exporter

- Обнаружено, что `pg_up` всё время равнялся нулю: экспортер отвечал Prometheus, но не мог
  подключиться к базе. Цель при этом была зелёной — её состояние говорит лишь о том, что
  экспортер жив, а не о том, что он достучался до PostgreSQL.
- Причина: пароль передавался внутри строки `postgresql://user:pass@host`, и символы `/` и `+`
  ломали разбор URL. Заменено на три отдельные переменные `DATA_SOURCE_URI`, `DATA_SOURCE_USER`,
  `DATA_SOURCE_PASS`.
- Поломку нашла подготовка алертов — до этого дашборд PostgreSQL просто стоял пустым.

### Алерты

- Настроен бот в Telegram и контактная точка в Grafana, уведомления идут в личный чат.
- Заведены пять правил: API недоступен, PostgreSQL недоступен, диск выше 85%, память выше 90%,
  доля 5xx выше 5%.
- Первая версия правил давала ложные срабатывания `DatasourceNoData`: сравнение стояло прямо
  в PromQL, и при нормальном состоянии запрос возвращал пустой результат. Исправлено переносом
  порога в блок Threshold — запрос теперь всегда возвращает число.
- Проверено на настоящем отказе: `dc stop api` → уведомление в Telegram → `dc start api` →
  уведомление о разрешении.
