# ADR-001: Versioned Snapshot Storage for Config Sections

**Статус:** Accepted  
**Дата:** 2026-06-09  
**Автор:** GameServer team  
**Связанные документы:** [CONFIG_SERVER_API.md](CONFIG_SERVER_API.md)

## Контекст

Новый Config Server API обслуживает игровой клиент, который синхронизирует конфиги
по секциям (`books`, `locations`, `requests`, `events`) через два публичных метода:

- `GET /api/v1/configs/manifest`
- `GET /api/v1/configs/{name}`

Клиент уже реализован и ожидает следующий контракт:

- сервер отдаёт список секций с `name`, `version`, `etag`
- затем клиент запрашивает конкретную секцию как **цельный JSON-массив**
- кеширование работает через `ETag` и `If-None-Match`
- `manifest[name].etag` должен совпадать с `ETag` публичного `GET /configs/{name}`

Админский API публикует новую версию секции целиком, поддерживает историю версий,
optimistic concurrency через `If-Match` и rollback на предыдущую версию.

Нужно было выбрать модель хранения для серверной части.

## Решение

Хранить каждую секцию как **версионируемый snapshot целиком**:

- одна строка в таблице `configs` = одна версия одной секции в одном environment
- поле `json` хранит **весь JSON-массив секции**
- публикация создаёт **новую строку**, а не обновляет существующую
- публичный API всегда читает последнюю версию секции
- rollback создаёт новую версию на основе содержимого старой версии

Пример модели:

```sql
configs(
  name        text,
  environment text,
  version     bigint,
  etag        text,
  json        jsonb,
  updated_by  text,
  updated_at  timestamptz,
  comment     text,
  primary key (name, environment, version)
)
```

## Альтернативы

1. **Строка на книгу / запись / событие, секция собирается на чтении**
   Плюсы:
   - удобно адресно менять отдельные элементы
   - проще делать выборки по конкретным полям SQL-запросами

   Минусы:
   - клиент всё равно потребляет секцию целиком, а не поэлементно
   - нужно отдельно вычислять общий `etag` для всей секции
   - rollback должен восстанавливать согласованный набор строк, а не один объект
   - усложняется optimistic concurrency на уровне всей секции

2. **Отдельная текущая таблица + отдельная таблица истории**
   Плюсы:
   - быстрее читать текущую версию без поиска `MAX(version)`
   - можно разделить hot path и history

   Минусы:
   - больше логики синхронизации между current/history
   - выше риск расхождения между текущим состоянием и историей
   - для MVP это усложнение без явной необходимости

3. **Хранить конфиги как файлы в object storage / Git / файловой системе**
   Плюсы:
   - просто просматривать и редактировать вне БД
   - удобно интегрировать с внешним редактором

   Минусы:
   - сложнее обеспечить атомарную публикацию, историю и concurrency через HTTP API
   - усложняется быстрый server-side доступ к последней версии
   - rollback и аудит пришлось бы реализовывать отдельно

## Почему выбрано именно это решение

- Клиент уже работает с секциями целиком, а не с отдельными объектами.
- `ETag` нужен на уровне всей секции, поэтому snapshot-модель естественно
  соответствует публичному контракту.
- История версий и rollback проще всего реализуются как append-only storage.
- Модель минимизирует серверную сложность MVP и количество специальных случаев.
- Публикация, rollback и promote работают в одной и той же модели: создать новую
  версию секции с новым `version` и соответствующим `etag`.

## Последствия

**Плюсы:**

- простой и предсказуемый контракт между клиентом и сервером
- прямое соответствие публичному API `manifest -> section snapshot`
- прозрачная история изменений
- простой rollback: копирование старого snapshot в новую версию
- естественная поддержка `ETag`, `If-None-Match` и `If-Match`

**Минусы / риски:**

- нельзя "добавить одну книгу" без перепубликации всего массива `books`
- любые правки одной записи создают новую версию всей секции
- размер одной строки растёт вместе с размером секции
- SQL-аналитика по отдельным полям секции менее удобна, чем при нормализованной модели

**Что становится сложнее для пользователей admin API:**

- перед изменением секции нужно сначала сделать `GET /api/admin/configs/{name}`
- затем изменить локальную копию массива
- затем выполнить `PUT` всего массива с актуальным `If-Match`

## Client/API Impact

- `GET /api/v1/configs/manifest` возвращает список секций с `etag` последней версии
- `GET /api/v1/configs/{name}` возвращает цельный JSON-массив секции
- `PUT /api/admin/configs/{name}` публикует не один элемент, а **новую версию всей секции**
- если пользователь хочет добавить, обновить или удалить одну книгу, он фактически
  публикует новый snapshot массива `books`

## Follow-up

- Если размеры секций вырастут существенно, пересмотреть:
  - лимиты размера snapshot
  - сжатие
  - возможное разделение крупных секций
- Если появится потребность в адресном редактировании элементов, рассмотреть
  отдельный editor-layer поверх текущей snapshot-модели, не ломая public contract.
