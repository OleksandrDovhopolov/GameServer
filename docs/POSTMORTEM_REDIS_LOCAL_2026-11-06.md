# Учебный инцидент: остановка Redis в локальном staging

Дата: 6 ноября 2026. Окружение: локальный Docker Compose на ПК. Публичный staging на Hetzner и Railway не затрагивались.

## Что произошло

Redis был намеренно остановлен командой `docker compose --env-file .env.staging -f docker-compose.staging.yaml stop redis`. Это учебный сценарий, а не непредвиденный отказ.

## Наблюдения и диагностика

- `curl.exe http://localhost:5080/ping` продолжил возвращать `pong`.
- `scripts/smoke-test.ps1` завершился с `[FAIL] service "redis" is not running`.
- `docker compose ... ps -a` показал API работающим, PostgreSQL в состоянии `healthy`, Redis в состоянии `Exited (0)`.
- В логах Redis видны `Received SIGTERM`, сохранение RDB на диск и штатное завершение. В логах API запросы к `/ping` завершались HTTP 200; ошибок Redis в просмотренном фрагменте не было.

## Причина и влияние

Непосредственная причина — ручная остановка контейнера Redis. `Exited (0)` и записи о сохранении указывают на штатное завершение процесса. При этом проверка `/ping` не проверяет зависимость API от Redis и потому не обнаружила остановку.

Подтверждено только отсутствие Redis во время проверки и отказ smoke test. Влияние на игровые операции и сохранность данных этим упражнением не проверялись. Время от остановки до восстановления не измерялось.

## Восстановление

Redis запущен повторно через `docker compose --env-file .env.staging -f docker-compose.staging.yaml start redis`. Пользователь подтвердил, что после запуска локальный smoke test проходит. Данных о потере пользовательских записей нет; отдельная сверка записей не выполнялась.

## Вывод и следующий шаг

Для диагностики доступности одной проверки `/ping` недостаточно. Если понадобится контролировать готовность игровых запросов, следует добавить отдельную проверку критичных зависимостей и проверить её на таком же сбое. `/ping` можно сохранить как простую проверку ответа HTTP-процесса.
